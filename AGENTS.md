# Working in kururu-styles

You are probably here because somebody said "add my theme to kururu" or "make me
a skin". This file is the operational brief for doing that without a human having
to send the pull request back.

Read [CONTRIBUTING.md](CONTRIBUTING.md) for what each field means — it is written
for people and it is accurate. This file is what you do, in order, and what will
bite you.

## What this repository is

Data, not code. Four kinds of entry, one directory each, one JSON manifest each.
Nothing here is built, imported, or executed. Kururu fetches `index.json` from
`raw.githubusercontent.com` and copies what somebody picks into
`~/.config/kururu/styles/`.

```
themes/<id>/theme.json      a complete palette
skins/<id>/skin.json        a difference from kururu's base shape
mascots/<id>/mascot.json    + sheet.png
packs/<id>/pack.json        three ids
index.json                  GENERATED — do not edit
schema/tokens.json          the token vocabulary. Read it; do not invent tokens
```

## The loop

```sh
node tools/validate.mjs
```

That is the whole review. Plain Node, no dependencies, no install step, and it is
byte-for-byte what CI runs. Run it after every edit. Do not open a pull request
on a failing run and do not "fix" the validator to make your entry pass — if the
validator is genuinely wrong, say so in the pull request and leave it alone.

Do **not** run `node tools/build-index.mjs` as part of adding an entry. The index
is regenerated by CI after the merge. A regenerated `index.json` in a branch
conflicts with every other open pull request, and reviewers have to read a diff
of digests to find the one line you meant.

## Adding an entry, step by step

1. **Pick an id.** Lowercase letters, digits and dashes; it must equal the
   directory name. It becomes a path on disk and a URL segment.
2. **Copy the nearest existing entry** rather than starting from the document.
   `cp -r themes/nord themes/my-theme`. The existing ones are known-valid and
   show the field order.
3. **Set `version` to `1.0.0`** for a new entry.
4. **Fill in `name`, `description`, `author`, `licence`.** The description is one
   line, 200 characters at most, and it is shown under the name in Settings —
   write what kind of thing this is, not that it is a theme.
5. `node tools/validate.mjs`
6. One entry per pull request unless they genuinely belong together (a pack and
   the three things it names is one pull request).

## The rules you will trip over

**Never write a URL into a manifest** except `homepage` and `source`, which are
credits. No `@import`, no `url(https://…)`, not in a token, not in a stylesheet,
not in a font declaration. Ship the file in your own directory. This is refused
by CI and refused again by kururu at install time, and the reason is not
aesthetic: a window that fetches an asset from somebody else's host tells that
host when its owner is working, and kururu is open all day.

**A theme is complete; a skin is a difference.** Do not "tidy" a theme by
deleting tokens that look like duplicates of each other — `text` and `textStrong`
being equal is a legitimate answer for a palette whose neutral ramp ends there.
Do not pad a skin out to the full token list; write only what you move.

**Changing an existing entry means bumping its `version`.** CI computes a digest
over the entry's files and refuses a changed digest under an unchanged version.
This is the single most common reason a pull request fails here. Patch for a fix,
minor for anything a person would notice, major if a file name or an id moved.

**Do not touch `schema/tokens.json`.** It is generated from kururu's own source
and is the contract. A token that is not in it is a token kururu does not answer
for, and adding it here does not make kururu draw it — it makes the validator
stop catching the mistake.

**Do not touch `index.json`.** Generated. See above.

## Skins with pictures

A skin's `parts` name PNGs in its own directory and say how each is cut. The
things that go wrong:

- **A part name is one of thirteen** — `schema/tokens.json` lists them under
  `skin.parts`. It names a region of the window (`statusbar`), never a class.
- **A slice has to leave a middle.** Top plus bottom no more than the picture's
  height, left plus right no more than its width. The validator checks this
  against the PNG's real size.
- **`scale` is a whole number, 1 to 8.** Pixel art is drawn small and shown big;
  a `2.5` would blur it and is refused.
- **`colors` takes the theme's `ui` names only.** No terminal colours. A skin
  drawn for a palette ships the palette as a theme and the two as a pack.
- **Put a `shot.png` beside the pictures.** The Styles tab draws the card from
  it; without one the card falls back to a box drawn from the tokens, which for
  a picture skin says nothing.
- **Do not hand-draw what `tools/art.mjs` generates.** `skins/ironclad` and
  `skins/handheld` are code; change the script and rerun it.

The fastest route is kururu's own *Settings → Skin studio*, which writes this
exact format to `~/.config/kururu/styles/skins/<id>/`. Copy the folder in.

## Mascots specifically

The sprite work is the part an agent gets wrong. Kururu wants **one sheet, square
cells, one clip per row**, and most asset packs ship one strip per animation at a
non-square cell width. Converting is not just a crop:

- Crop every frame to the **union** bounding box of *all* frames of *both* clips,
  then centre that in a square cell. Never per frame and never per clip.
  Per-frame trimming throws the animation away — where a sprite sits in its cell
  is how a sheet draws a hop, so trimming each frame to its own content lands them
  all on the floor. Per-clip trimming makes the sprite change size the moment its
  agent stops working.
- `trim` in the manifest is the same one box, expressed inside the cell.
- Check the result at **16px**, because that is the badge. Tall silhouettes
  survive it; wide ones letterbox to half height.
- Keep the PNG under a megabyte, and well under it. The reference frog is 15KB.

Licence matters more here than anywhere else in the repository, because sprites
are the one thing people lift without checking. If you cannot name the licence
and link the source, do not add it. "Found on the internet" is not a licence, and
neither is an asset pack whose only documentation is a thank-you note.

## What a good pull request looks like

- One entry, one directory, no changes outside it.
- `node tools/validate.mjs` passes.
- The pull request body says what it is, where any third-party work came from,
  and under what licence.
- No changes to `index.json`, `schema/`, or `tools/`.

## If you are also working in kururu itself

Kururu is a separate repository and this one must not learn about its internals
beyond `schema/tokens.json`. If a style needs a token that does not exist, that
is a change to kururu's `shared/skin.ts` or `shared/theme.ts` first, then a new
`schema` here — not a token invented in a manifest, which validates nowhere and
draws nothing.
